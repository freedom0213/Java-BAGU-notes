# 五、消息队列（45 题）

### （一）通用基础

#### 1：为什么需要消息队列？解耦、异步、削峰填谷分别解决什么问题？

在回答为什么需要消息队列的时候，就需要从 使用消息队列带来了什么改变？  
很显而易见的就是代码解耦了，比如订单业务创建订单完毕后 往往需要去库存那里扣减库存，甚至说还需要发布短信之类的服务，如果不使用消息队列的话，那么业务关系就是订单->库存->短信，那短信服务需要一直等待库存业务执行完毕，然而实际情况上一些服务并不需要等待另一个服务成功与否，两个服务是并行关系而不是继承关系，所以使用消息对立可以将业务解耦，降低业务之间的关联性。  
所以从这里也可以看出消息队列还有另一个优点就是异步性，极大的提高了业务执行性能。  
最后优点就是削峰填谷：消息队列可以做到对瞬时的大请求量进行限流，然后等到高峰期结束，消息队列就可以将之前MQ内挤压得消息给处理了。  

#### 2：引入 MQ 之后带来了哪些新的复杂性问题？

1：最明显的就是消息可靠性问题，消息可靠性问题分成：生产者是否可靠，MQ是否可靠，消费者是否可靠  
具体就是：  
在生产者发送消息的时候，需要确认MQ是否接收->MQ将会发送生产者ACK消息表示MQ接收消息成功  
MQ储存消息，如果MQ宕机消息不就没有了吗？->MQ持久化：交换机 消息队列 还有消息都持久化  
MQ怎么知道消费者到底是否成功消费消息了呢？->消费者完成消费返回MQ ACK表示消息消费成功  
其它的就是：  
2：消息重复消费：比如MQ发给消费者消息，但是消费者很长时间没有返回消息，MQ以为消费者挂了就又发送了消息，然后消费者重复消费->消费者幂等消费。  
3：消息消费者执行失败：比如扣库存业务扣库存但库存不足，扣库存失败->多次重试+死信队列+人工干预  
4：消息积压：也就是MQ消息传来速率<消息消费速率，这时候消息就会慢慢的在MQ内部挤压->提高消费水平比如增加消费者。  
5：消息顺序：消息执行顺序不对，也就是因为消息进入消息队列后，因为queue绑定了多个消费者，各个消费者执行消息速度不一样，导致顺序不一致->解决方法：对于同一个订单的消息 确保消息都进入同一个队列（比如使用rountingkey或者对于orderid哈希计算），并确保监听队列的消费者只有一个。  

#### 3：消息队列的两种消息模型（点对点 / 发布订阅）有什么区别？

点对点：一条消息，多个人抢着干，最终一个人干。  
发布订阅：一条消息，多个人各自都要知道，各自都收到。  

#### 4：主流 MQ 对比（Kafka、RocketMQ、RabbitMQ、Pulsar）？各自特点和适用场景？

主流的消息队列主要有 RabbitMQ、Kafka、RocketMQ 和 Pulsar。  
RabbitMQ 使用比较简单，Exchange 和 RoutingKey 提供了灵活的消息路由，通过将消息利用交换机和rountingkey传递到指定的消息队列，从而保证消息在队列的有序性，同时 ACK、死信、TTL 等机制比较完善，比较适合微服务中的业务消息。  
Kafka 更偏向高吞吐和大规模消息处理，通过 Topic 和 Partition 实现水平扩展，其中Topic是指消息的分类：Kafka->topic:order->partition 0，也就是对于都是订单的消息会分配到topic:order下，然后每一个topic下都有很多队列Partition，通过对key哈希计算从而将同一个业务消息放在同一个消息队列中；消息可靠性方面也是分为3部分：  
生产者->kafka：acks机制；  
kafka本身消息可靠性：每一个Partition有多个副本+持久化，保证安全性和高可用性；  
消费者：Offset机制：Partition其实是一个消息队列，每一个消息在队列中都有下标，offset就是记录消息执行到哪一个下标的消息；  
比较适合日志、埋点、数据管道和流式处理。  
RocketMQ 是阿里开源的消息中间件，比较适合电商和交易类业务，对顺序消息、延迟消息、事务消息等业务场景支持比较丰富。  
Pulsar比较少用

### （四）RabbitMQ

#### 29：RabbitMQ 的核心概念（Exchange、Queue、Binding、RoutingKey、vhost）？

Exchange：交换机  
Queue：消息队列  
binding：绑定关系 也就是交换机会和队列之间绑定，通常是使用bindingkey关联，需要配合routingkey使用。  
RoutingKey：消息层面的东西，发送消息的时候消息携带者RoutingKey，交换机会根据RoutingKey和bindingkey来进行路由。  
vhost：虚拟主机，相当于git的分支，当场景不同，比如测试，生产，开发属于不同的环境，不同的环境可能使用的交换机队列有重复的，所以需要vhost进行权限隔离。  

#### 30：RabbitMQ 有哪几种交换机类型（Direct、Topic、Fanout、Headers）？

首先我们要知道交换机类型意思是 交换机如何将消息通知到消息队列 最常见的Direct 和 Topic类型交换机，Direct：也就是bindingkey==routingkey，准确判断，当这个交换机类型是Direct时候，消息传到这个交换机会准确地拿bindingkey==routingkey判断；Topic：通配符匹配，比如order.*/order.#前者地通配符匹配一个字符，后者匹配多个，也就是当消息传递到交换机的时候携带的routingkey是order.create，由于交换机类型是topic：order.*类型，那么交换机中通过bindkey为：order.*绑定地队列都会接收这个消息。  
还有一种类型是Fanout：广播，这种类型地交换机不关系bindkey和routingkey，收到消息的时候会把消息发布到所有绑定地队列。  
不常见的是Headers：是根据Header配置匹配，很少用。  

#### 31：RabbitMQ 如何保证消息不丢失（生产者确认、持久化、消费者手动 ACK）？

RabbitMQ 保证消息可靠性主要从三个环节入手。首先生产者开启 Publisher Confirm，确保消息成功到达 RabbitMQ；其次对 Exchange、Queue 和消息本身进行持久化，避免 RabbitMQ 重启导致消息丢失；最后消费者采用手动 ACK，只有业务处理成功后才确认消息，如果消费者处理过程中宕机且没有 ACK，RabbitMQ 会重新投递消息。  
但并不会100%保证消息不丢失。  

#### 32：RabbitMQ 如何用 TTL + 死信队列实现延时消息？

从代码层面就是：先创建延迟队列和延迟交换机，当然还需要绑定关系，然后再创建死信交换机和死信队列和死信bindingkey：dead，然后再在配置类中配置延迟队列，明确配置属性：TTL，deadLetterExchange("dead.exchange")，deadLetterRoutingKey("dead")，其中后面配置意思是：如果消息在延迟队列到达TTL后还没有被消费就会被死信交换机分配消息(dead.exchange)------(dead)------>死信队列delay.queue。  
配置完毕延迟消息执行顺序：延迟交换机->延迟队列->TTL过期->死信交换机->死信队列  
至于死信队列的死信消息如何处理，就交给业务专门监听delay.queue队列，进行取消业务。  

#### 33：Connection 和 Channel 是什么关系？为什么需要 Channel？

Connection 是客户端与 RabbitMQ 之间建立的 TCP 连接，而 Channel 是建立在 Connection 之上的逻辑通信通道。RabbitMQ 的生产、消费、ACK、声明队列和交换机等操作通常都通过 Channel 完成。之所以引入 Channel，是因为创建 TCP Connection 的成本比较高，可以让多个 Channel 复用同一个 Connection，从而减少 TCP 连接数量，降低资源消耗。  

#### 34：RabbitMQ 的集群模式和镜像队列（Quorum Queue）原理？

首先我们要知道 为了保证RabbitMQ可靠性，需要利用RabbitMQ的持久性就是为了解决RabbitMQ宕机后能够快速读取文件获取数据快速恢复，但是即使你恢复速度再快，也会有那么一段时间，MQ处于宕机状态，所以为了使得rabbitMQ的高可用性，需要部署多个RabbitMQ实例，所以这时候需要RabbitMQ集群模式。  
但是正常普通RabbitMQ集群是不可能地把一个消息复制到其它所有节点同步地，因为这样普通复制地方式你必须要使得所有节点对于同一个消息消费是否地同步，很麻烦，所以这里结合着Quorum Queue，Quorum Queue本质是一个队列，里面记录着消息的副本，比如对于消息Message:1，里面会记录着这个消息的各个副本1，2，3然后还会记录各个副本存储在哪些节点，其中会以某一个节点为Leader表示这个节点优先处理这个消息，当这个节点挂了，Quorum Queue就会筛选节点挑选一个节点作为Leader来处理消息。
