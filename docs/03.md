#### 1：Redis 有哪些数据类型？各自的使用场景是什么？

Redis有5个基础数据类型：String Hash List Set ZSet  
其中String是最常见的redis数据类型，应用于：缓存，计数器，分布式锁 这种对Value值比较重要的场景  
缓存：就比如记录商品product:1001->json，这样子通过key获取value；计数器：比如现在product:1001->100，然后通过命令可以直接作用于这个product:1001这个key，进行计数；分布式锁：就很经典的Set lock:lock 1 NX EX 20  其中lock:lock为key 1为String值  
Hash：Redis中再套一层key-value，变成key-field-value这样结构，通常在有结构性数据的时候会使用  
List：可重复有顺序列表，一般用于消息队列或者延迟队列，但有更好的选择：RabbitMQ  
Set：不可重复随机表：一般场景用于去重，比如key表示一个用户user:A 那么value就是A用户的好友列表  
user:A->{B,C,D}这时候如果使用添加好友命令就会去重  
ZSet：在Set基础上加一个属性Score分数，所以ZSet可以变成有序的，使用场景比如积分排行，可以根据Score排行也可以根据Score查询  
还有一些其它的数据类型，比如很经典的：bitMap是Redis基于String类型实现的一种结构，一种以具体日期为key，签到布尔值字符串为key，比如：sign:2026:01-> 1001111100...  value30节长度表示具体各个日期的签到情况。  

#### 2：SDS 相比 C 字符串有什么优势？为什么这么设计？

首先C字符串其实是一种字符数组这样的形势：char str[]="hello"，然后存储形式是：h e l l o \0,一共5+1个字符，最后的字符是\0表示这个字符串的截至位置，所以当需要获取这个C字符串长度的时候就需要遍历这个字符串找到\0位置才行，但是对于redis来说 需要经常操作访问字符串，如果每一次获取字符串长度都需要遍历一下就太浪费时间了，所以需要redis自己实现的一种字符串结构SDS  
SDS结构具体是分为：[len][free][data]/0，len表示字符串长度，free表示字符串还剩余的空间，data才是真实的数据，/0依然表示字符串截至位置但SDS结构并不依靠/0获取长度而是依靠len，那为什么还保留呢？是因为为了兼容一些C语言函数。  
优势：1:对于Redis经常对字符串访问操作的环境下，使用SDS能快速获取字符串长度数据，从O(n)->O(1)  
2:避免缓冲区溢出：C字符串在使用追加字符串的时候，可能会超过数组大小，而SDS在追加时，会进行计算确保当前字符串预留空间够字符串的扩增。  

#### 3：跳表的原理是什么？ZSet 为什么用跳表而不是红黑树？

跳表原理就是基于底层的有序链表10-20-30-40-50然后再加多层有序链表10-30-50，上面的这些有序链表就可以作为索引快速定位具体元素的位置，而红黑树原理其实就是一个自平衡二叉搜索树，普通二叉搜索树类似于每一个树节点左子节点<根节点<右子节点这样的顺序，但是会出现一个问题，如果根节点是10，然后所有子节点都比10大，那么节点就会向右子节点倾斜，造成树特别高，这时候就需要红黑树经过颜色计算可以将二叉搜索树进行平衡高度，这样也能达到快速查询的特点。  
但对于ZSet来说，使用的是哈希表(类似于hashmap key-value结构)+跳表而不是使用红黑树表  
然后现在来说ZSet底层结构：因为ZSet存在score属性，所以在存储数据的时候，一般是liming  20,daming  30,wangwu  40这样的结构，很明显想要同时知道谁的分数和分数是谁需要使用key-value结构，所以需要使用哈希表，但是在存储的时候并不是有序的可能是乱序的，所以要想快速查询分数和排序就需要利用跳表  
为什么不使用红黑树？：因为红黑树代码复杂度要高得多并且还需要维护平衡

#### 6：Redis 为什么这么快？（请从内存、线程模型、IO 多路复用、数据结构四个维度回答）

内存：比如走MYSQL的话，需要请求到达数据库然后读硬盘然后返回数据，光是都硬盘操作就很慢，而redis数据都在内存中，读内存操作比读硬盘快多了  
线程模型：Redis的核心操作并不是在有多请求的时候是多线程操作而是单线程循环使用，为什么？因为多线程操作一直有一个弊端就是会涉及多线程的切换，锁的抢用，阻塞步骤，这样必定会有时间开销  
IO：redis使用IO复用，也就是并不是给每一个客户端都分配一个专属线程而是使用一个公共线程，哪个客户端有真实的IO操作就会调用线程  
数据结构：redis的数据类型很高效  

#### 7：Redis 为什么设计成单线程？6.0 为什么又引入多线程 IO？

因为即使Redis有那么多优点是的redis效率特别快，但是如果真的出现那么多请求需要使用线程，甚至说某一个客户端在线程上作用太长时间，单线程IO复用是有瓶颈的，所以引入了多线程IO复用。  

#### 8：Redis 的 IO 多路复用是怎么工作的？epoll 的作用是什么？

RedisIO多路复用其实就是一个循环过程while(redis运行){监听epoll带来的消息->socket时间传来消息(需要读取请求)->对消息进行处理}，epoll其实就是一个对客户端的一个监听器，哪个客户端传来IO请求消息就发消息给redis，让redis单线程复用处理请求。  

#### 9：Redis 的过期删除策略是什么？（惰性删除 + 定期删除）

redis的过期删除策略是惰性删除+定期删除：一般在存储数据的时候会设置EX30也就是TTL，当时间超过了过期时间就会进行删除，但这时候删除并不是直接物理删除，因为如果让每一个数据都按时定时删除，那么需要定时任务，那么几千个数据就需要几千个定时任务，每一个定时任务都需要独立执行，特别消耗cpu资源，所以在到期的时候就先不删除，先进性逻辑删除，当再次访问数据的时候发现已经到期就会对它进行物理删除，但是如果过期后再也很久不访问数据的话，这个数据就会一直存在，苏哦一就需要定期删除，多次，少量周期性检查。  

#### 10：Redis 的内存淘汰策略有哪些？LRU 和 LFU 的区别？生产怎么选？

redis的内存淘汰策略和过期删除策略不同，过期删除策略是指数据到达过期时间该怎么处理，而内存淘汰策略是指redis的内存用完了，该使用的策略，redis的内存淘汰策略有三种：  
1：直接拒绝，不删除老数据，直接拒绝新数据  
2：LRU：R：recently最近，也就是优先删除最近没有被使用的数据  
3：LFU：F：fluent频繁，也就是优先删除使用次数最少的数据  

#### 11：RDB 和 AOF 的原理与区别？生产环境如何选择？

RBD和AOF都是redis持久化的一种策略，其中RBD是指定时的将redis的整个数据集保存到rdb文件中作为一个数据快照，好处是文件大小小，恢复速度快，但是问题是数据可能记录的不够准确，比如当还没到生成rdb文件时候，就有一个写操作，但是同时redis挂了，那么这个写操作就丢失了  
AOF原理是将redis中写的操作都记录在aof文件中，Redis 重启时通过重新执行这些命令恢复数据。AOF 数据安全性更高，但文件通常更大，恢复速度相对较慢  
在实际生产环境中通常两个会结合使用，比如当redis通常挂了，需要恢复的时候默认使用aof，但如果场景是第一次使用主从关系redis需要全量复制同步数据的时候就是用rdb策略。  

#### 12：Redis 7 的混合持久化是什么？解决了什么问题？

redis7的混合持久化就是一个aof文件中存在aof+rdb数据，当一个aof文件写的操作越来越多的时候，这个文件会越来越大，通过aof恢复数据的时间就会越来越长，所以就可以将aof文件中的前100w个写操作数据集作为一个rdb快照文件，之后后续继续记录写操作，这样恢复的时候先读取rdb文件，然后再只需要读取aof的100条写操作数据即可。  

#### 13：AOF 的三种写回策略（always / everysec / no）及各自的数据安全风险？

always也就是有一个写操作就需要同步更新aof文件，安全性最高，效率最低  
everysec每秒做一次更新aof操作，默认用这个  
no：redis不管理更新aof操作，交给系统业务完成  
其中aof详细的策略需要理解下，并不是说redis有一个写操作，就直接写在aof文件中就写入磁盘了，真实情况是，当redis有些操作的时候，会先执行写命令，之后会将这个命令作为aof buffer写在redis内部缓存中，接下来会经过系统调用写在系统缓存中，最后落到硬盘中。  

#### 14：AOF 重写的过程是怎样的？为什么要重写？重写时会阻塞吗？

为什么需要aof重写机制？是因为如果aof记录了很多对于id=1的写操作，比如记录了100条，但是最终redis内存数据结果实际上是第101条写操作结果，那么前100条就没意义了，所以就需要aof重写机制  
那重写机制是怎么实现的呢？当触发重写机制的时候主线程fork会创建一个子进程检查当前内存数据专门再做一个aof文件记录更简洁的写操作，同时主进程在创建子进程后，会继续接收写命令记录下去，在aof创建完成后会将之后日志追加到aof文件中。  
阻塞：其实本身aof重写机制没有阻塞显现，因为创建aof文件是在子进程完成的，唯一阻塞是发生在主进程创建子进程操作，期间会拒绝接收日志。  

#### 15：bgsave 生成 RDB 时如何做到不阻塞？写时复制（COW）的原理和代价？

首先 我们要知道bgsave是什么，其实bgsave是redis的一个生成rdb文件的命令，与save命令不同，bgsave是主进程生成一个子进程，子进程用来生成rdb文件，但是问题来了，子进程怎么读取数据？这时候就需要COW（copy on write机制）：也就是主子进程共享一个内存数据，但是如果在生成rdb文件的时候，主进程又有新的写操作，这时候就需要对这个数据页复制一份，主进程修改复制页的数据，这就是写的时候才复制。  
代价：Redis 在 BGSAVE 期间可能出现明显的额外内存开销，fork 本身存在短暂阻塞。  

#### 16：Redis 主从复制的原理？（全量复制与增量复制的触发条件）

redis主和从第一次建立关系的时候会通过全量复制，也就是主通过bgsave创建子进程，然后子进程创建RDB文件记录数据集快照，同时创建快照时候主进程还能正常接收写操作，创建完毕然后从加载RDB后再接收同步期间产生的增量写命令。  
如果主和从已经建立过关系，如果只是因为网络波动，导致主还留着要同步到从的复制挤压缓存区数据，这时候可以使用增量复制，但是如果主和从数据差距过大，或者复制挤压缓存区数据消失不见了就会继续使用全量复制。  

#### 17：repl_backlog_buffer 和 replication buffer 的区别是什么？

repl_backlog_buffer就是我上面所说的复制挤压缓冲区，这个复制挤压缓冲区是放在主节点上，用于将主的数据同步到所有绑定的从节点上；而replication buffer是专门用于准备发给某一个从节点的数据，比如repl_backlog_buffer此时记录着所有待同步的数据，但是由于两个从节点，s1网路速度比s2慢，所以就导致需要缓冲区，当主的写操作生产的太快，从节点应对不过来的时候就需要缓冲区replication buffer，记录着从待解决处理的数据。  

#### 18：哨兵机制的原理？主观下线和客观下线的区别？

哨兵机制就是redis会有许多哨兵，这些哨兵会时刻（周期性的）检查各个节点的生命情况，当主节点被一个哨兵判断为死亡时候，是主观下线，当多个哨兵（具体是在redis sentinel中的quorum配置数量） 比如3个哨兵都判定是死亡，这时候所有哨兵会选举一个哨兵会作为处理主节点死亡事件的管理者Leader，这个管理者会根据相关配置选举一个从节点作为主节点，然后从新建立起主从之间的网络联系。

#### 20：Redis Cluster 的实现原理？哈希槽为什么是 16384 个？

#### 22：Cluster 和 Sentinel 的区别？如何选型？

这个很重要，Cluster是一种分布式集群方案，用来解决只有一个master放不下有几百万个key，大大减低性能的情况，这时候使用分布式集群创建多个master分配数据，减少压力，并且还能利用哈希槽思想，快速找到所对应的数据，同时Cluster中每个master也配置的有从节点，来确保redis集群的高可用性

#### 23：Redis 集群会出现脑裂吗？如何避免（min-replicas-to-write）？

会，只要有主从恢复机制，都有可能概率上存在脑裂情况，如何避免？redis使用min-replicas-to-write机制，意思是说，master要能成为master必须至少有一个符合条件的Slave跟随自己，才允许执行写操作。  
但实际上min-replicas-to-write配置不能完全防止脑裂情况发生，只能说减少了概率情况，因为网络问题是很复杂的。  

#### 24：缓存穿透、缓存击穿、缓存雪崩的区别？各自的解决方案？

缓存穿透：是指select一个数据user:999，缓存内没有，数据库也没有，但是此时如果来一堆1000个请求都是访问user:999的这种不存在数据，这个请求就会经过mysql查询，直接打在数据库中。  
方案：1：缓存空对象：当客户端请求一个redis不存在数据，并且mysql数据库也不存在数据时候，会立即在redis中生成一个user:999 = null的数据，之后再请求这个user:999会直接返回null；2：布隆过滤器：布隆过滤器可以快速查询一个数据在redis中是否存在（请求不需要过redis或数据库，只经过布隆过滤器），如果布隆过滤器判断不存在，那么一定不存在，如果存在则可能不存在。  
缓存击穿：是指一个热门商品，很多客户端都会访问这个数据，所有redis中有很多线程请求就会打在这个数据上，但是突然比如TTL时间到了，导致商品数据消失，然后所有大量数据请求都会打在数据库上面。  
方案：1：互斥锁，每一个请求访问redis都会竞争枪锁，这样做可以大大减少请求数量；方案2：逻辑过期。也就是商品到达TTL后，并不会立即删除，而是返回旧数据+异步更新缓存数据，这样数据还是打在redis上面。  
缓存雪崩：同一段时间突然大量数据过时，导致大量数据请求打在数据库上。  
方案：给缓存 TTL 增加随机值，让不同数据在不同时间过期。  

#### 25：布隆过滤器的原理？误判率？如何支持删除元素？

布隆过滤器本质是一个算法+数据结构，它有一个很长的二进制数组和多个哈希函数，当存redis数据的时候会将key进行三个哈希函数的计算，得到三个值，然后3个值 比如2 4 7然后去对应数组位置将0变成1，所以当再次查询这个key的时候，只需要计算key的多个哈希值就对应二进制数组都是1 能得知这个数据是在redis中存在的  
当然也会误判，比如经过哈希计算发现是存在的，但实际上是哈希碰撞了误判了，所以实际上这个查询的key并不存在，但经过布隆过滤器判断出不存在key，那么是一定不存在的。  
普通的布隆过滤器本身不支持删除元素，因为如果删除key对应的数组位置的话，会破坏其它元素数据，所以可以使用计数布隆过滤器解决，普通的是只有0 1两种方式，使用计数布隆过滤器：只要比如序号为1的位置，只有有数据的哈希值在这里存储，值加1，删除的化只需要数值-1即可。  

#### 26：缓存与数据库的一致性怎么保证？为什么推荐先更新 DB 再删缓存？

缓存与数据库不一致现象是因为修改缓存操作和修改数据操作所处是事务不一致，就会出现修改缓存成功但修改数据库失败的例子，所以为了保证两者的数据一致性，一般采用先修改数据库，数据库修改完毕会把缓存数据删掉，然后之后发来的请求数据访问redis会miss，然后继续访问数据库得到数据然后返回给redis重新写入缓存。  
为什么设计成这样？？因为归根结底，数据还是真正的存在mysql上，所以首先需要保证mysql的数据正确性，那为什么后面再来修改redis而是要删除呢？？因为删除最简单并且如果修改还是会经历可能失败数据不一致现象。  

#### 27：什么是延迟双删？为什么删两次还不够？

延迟双删是为了避免特别刁钻情况：当线程A修改数据a->b，修改mysql，并且提交，删除redis，但此时其实在线程A修改数据前，线程B就来访问redis但是由于redis数据各种问题导致数据丢失放生miss现象就会访问mysql，获得旧数据，返回redis时候发现没有数据就顺手写入redis ：a，s此时mysql：b，redis：a，出现了不一致现象。  
所以为了解决这一现象，使用延迟双删：① 更新 DB② 删除 Redis③ 等待一小段时间④ 再删除 Redis  

#### 28：基于 Binlog（Canal）同步缓存的方案原理及优缺点？

首页我们要知道什么是binlog和Canal：binlog是mysql中记录数据库修改数据操作的日志文件，所以当mysql开启事务执行修改数据时候，当事务提交后会生成binlog日志，之后会有Canal监控binlog日志，如果有新数据比如修改了id=1的数据，cannal就会异步消息通知消费者redis，然后redis会删除id=1的缓存之后会访问数据库回写。  
优点：效率比延迟双删要高，因为使用Binlog方法可以将mysql操作和redis依赖性大大降低，也就是将缓存同步与业务代码解耦了，但由于binlog+Canal本质是通过异步消息实现所以需要设计消息可靠性和幂等问题。  

#### 29：Redis 分布式锁怎么实现（SET NX EX + Lua 释放）？为什么必须用 Lua？

redis获取分布式锁本质就是使用redis命令：setnx： SET lock:product:1 uuidB NX EX 30。这个锁会先利用NX命令判断redis内有没有这个key类型的锁，如果没有这个锁才会创建这个锁，之后如果有线程在想获取这个同一个key的锁就直接返回false。那获取锁利用setnx，释放锁呢？？释放分布式锁利用lua命令，将判断锁是否自己的锁+释放锁 两个原子性步骤作为一个原子性操作。  
为什么需要判断锁是否是自己的？比如同一个线程，先获取一个分布式锁，但是由于一些原因，到达TTL后也没有释放锁，所以这时候执行兜底方案自动释放锁，释放锁后，之后又来一个客户端获得锁，但是上一个获取锁的业务执行完毕想要使用lua脚本释放锁，但是此时锁并不是原本的锁，该锁原本持有者：uuidB，判断锁的持有者发现现在该类型锁被uuidC持有，所以此时就不能lua脚本释放锁了，如果释放锁就会误删锁了。  
为什么必须用LUA？因为LUA脚本在redis有个特点，也就是当redis执行一个LUA脚本的时候，期间会停止其它一切行为，直到LUA执行完毕后才会接着做其它事情，而判断锁和删锁两个步骤理应是一个连续过程，所以使用LUA最合适。  
注意：分布式锁是有多个的，比如我创建一个分布式锁：set lock:user:1 uuidA NX EX 30，其中lock:user:1是key是锁的唯一标识，uuidA只是说整个锁被谁哪个线程持有，uuidA只是当前持有锁线程的别名，所以lua脚本判断锁的时候是要判断uuidA，竞争锁的时候竞争的同一个key的锁。

#### 31：Redisson 看门狗（watch dog）机制的原理？如何实现可重入？

redisson看门狗机制是为了解决执行业务时间超过TTL的时候，这个分布式锁该如何释放的问题。首先我们要知道redisson是一种对redis的封装工具，里面提供了许多java API，比如分布式锁的使用，在业务中我们很少使用redis手写创建锁维护锁之类的，因为这样子我们还需要自己考虑加锁，释放锁，续期等等，所以我们已使用redisson封装api使用分布式锁，比如RLock.lock()，就是创建一个redisson分布式锁，但redisson可以帮你判断锁，释放锁，可重入实现，锁续期等等。  
所以看门狗机制就是监控各个持有者持有锁的情况，比如TTL=30s，但直到30s后持有者还是没有释放锁，这时候看门狗就会不断对锁时间进行重置。  
Redisson 的 RLock 还是可重入锁。同一个线程再次获取自己已经持有的锁时，不会阻塞，而是增加该锁的重入次数；每次 unlock() 只减少一次重入次数，直到计数归零后才真正释放锁。这样可以避免同一线程嵌套调用时自己把自己阻塞。

#### 34：Redis 事务（MULTI/EXEC）和数据库事务的区别？为什么它不支持回滚？

redis事务不同于数据库事务，redis事务一般这样子写：  
MULTI  
SET user:1 张三  
SET user:2 李四  
INCR count  
EXEC  
其中MULTI表示开启事务模式，然后下面是需要打包起来的命令，注意执行MULTI的时候只是进入事务状态，后面的命令进入事务队列中，并没有执行，在执行EXEC后，才是真正准备执行。  
Redis相较于数据库事务，redis事务并没有回滚功能，而是类似于打包命令的功能，为什么没有回滚功能？因为redis事务设计指出就是为了避免在执行一些列命令的时候被插入其它命令，并且redis本身就是原子性操作，只要命令写的合理很少会出现执行失败需要回滚情况，并且如果真到了需要回滚情况，也不会回滚，因为只要涉及到回滚就需要记录相关log日志，redis以效率为主，并不会专门维护log日志。

#### 39：如何用 Redis 实现延时队列（ZSet / Stream / 过期监听）？

Redis 实现延时队列最常见的是 ZSet，将消息作为 member、执行时间戳作为 score，消费者定期查询 score 小于等于当前时间的消息，领取后执行并删除。也可以结合 Stream 实现延时调度和消息消费，或者利用 Keyspace Notification 监听 Key 过期事件，但过期监听可靠性较弱。实际生产中还需要考虑任务抢占、失败重试和幂等。
